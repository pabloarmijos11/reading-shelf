1. Contexto y objetivos

Reading Shelf permite buscar libros contra la API pública de Open Library, llevar una lista de lectura con tres estados (quiero leer, leyendo, leído) y agrupar los libros en estanterías propias. Las páginas de búsqueda y de ficha de libro son públicas; la biblioteca personal exige cuenta.

El objetivo del proyecto no era el catálogo en sí, sino construir una aplicación con la infraestructura completa que un producto real necesita: renderizado en servidor para que el contenido público sea indexable, reglas de seguridad que resistan a un cliente malicioso, y un pipeline donde las pruebas sean una puerta y no un informe que nadie lee.

2. Arquitectura

La aplicación se ejecuta en dos entornos distintos y esa separación gobierna casi todas las decisiones del proyecto. En el servidor se renderiza el HTML y se consulta Open Library; en el navegador viven la sesión y el acceso a la base de datos. Ningún dato privado se toca durante el renderizado en servidor, porque allí sencillamente no hay sesión.

3. Tres decisiones que definen el proyecto

3.1 Qué se renderiza en el servidor, y la única excepción deliberada

Casi todo se renderiza en servidor, porque casi todo es público y debe ser indexable. La búsqueda depende de un parámetro de consulta y la ficha depende de un identificador que solo existe en Open Library: ninguna de las dos puede generarse en tiempo de compilación, así que ambas se renderizan por petición.

La biblioteca personal es la excepción, y no por comodidad. Está protegida por un guard, y la sesión solo existe en el navegador: en el servidor no hay sesión que valga, de modo que el guard concluiría «nadie ha iniciado sesión» y redirigiría todas las peticiones al login, incluidas las de usuarios perfectamente autenticados. Renderizarla en cliente permite que el guard se ejecute donde la sesión realmente está.

// app.routes.server.ts
{ path: 'books/:id', renderMode: RenderMode.Server },  // público → SSR
{ path: 'library',   renderMode: RenderMode.Client },  // privado → cliente
{ path: '**',        renderMode: RenderMode.Server },

No se pierde nada: la página es privada, luego no tiene valor para un buscador, y sus datos tampoco podrían obtenerse en el servidor.

3.2 Firestore se carga bajo demanda, y solo en el navegador

Importar firebase/firestore de forma estática arrastra al bundle del servidor la compilación de Firebase basada en gRPC, que rompe las peticiones HTTP salientes de Angular durante el renderizado. La solución es un servicio que lo carga con un import() dinámico y que además responde si Firestore está disponible siquiera.

// firestore-loader.ts — el import dinámico es lo que mantiene
// firebase/firestore fuera del bundle del servidor.
this.instance ??= import('firebase/firestore')
  .then(({ getFirestore }) => getFirestore(this.app));

La regla se propaga a todo el código que lee o escribe: sus utilidades deben venir del mismo import dinámico, nunca de uno estático, o el problema regresa intacto. El efecto secundario es favorable: Firestore tampoco entra en el bundle inicial del cliente hasta que un usuario identificado lo necesita de verdad.

3.3 El guard espera a que la sesión se conozca

Firebase resuelve el estado de la sesión de forma asíncrona. Preguntar isSignedIn() de inmediato devuelve falso mientras la respuesta viaja, y el resultado es un usuario válido expulsado al login cada vez que recarga la página. El guard espera a que el estado esté resuelto antes de decidir y, si toca redirigir, recuerda a dónde iba el usuario.

if (!auth.ready()) {
  await firstValueFrom(toObservable(auth.ready).pipe(filter(Boolean)));
}
if (auth.isSignedIn()) return true;
return router.createUrlTree(['/login'], { queryParams: { redirectTo: state.url } });

Por qué importa. Es un fallo que no aparece en desarrollo: en local la sesión se resuelve tan rápido que el parpadeo pasa inadvertido. Tres de las pruebas del guard existen precisamente para cubrir el estado intermedio —sesión aún desconocida— que es donde vive el error.

4. Modelo de datos y reglas de seguridad

Cada usuario posee dos subcolecciones bajo su propio identificador. Esa forma es intencional: la ruta del documento contiene el dueño, así que la comprobación de propiedad no requiere leer el documento ni confiar en ningún campo que el cliente pueda escribir.

users/{uid}/books/{workId}     // lista de lectura
users/{uid}/shelves/{shelfId}  // estanterías

// Hora sellada por el servidor: el cliente no puede adelantar ni atrasar.
function isServerTime(value) {
  return value is timestamp && value == request.time;
}

function isValidEntry(data) {
  return data.keys().hasAll(['status', 'title', 'authors', 'updatedAt']) &&
         data.keys().hasOnly(['status', 'title', 'authors', 'coverId', 'updatedAt']) &&
         data.status in ['want', 'reading', 'read'] &&
         data.title is string && data.title.size() > 0 && data.title.size() <= 300 &&
         isServerTime(data.updatedAt);
}

Las reglas documentan también lo que no cubren: el tamaño de cada elemento de authors no se valida, solo el de la lista. Un usuario decidido podría guardar cadenas muy largas dentro de su propio documento; el alcance queda limitado a ese documento y al tope de 1 MB de Firestore, y el cliente trunca cada campo antes de escribir. Declararlo es parte del análisis: una regla de seguridad que se presenta como infalible es más peligrosa que una cuyos límites están escritos.

6. Integración continua y despliegue

El pipeline tiene tres trabajos encadenados y una regla que lo explica entero: el despliegue depende de las pruebas end-to-end. Si fallan, producción no se toca.

6.1 La verificación final: por qué no basta con un código 200

El último paso pide la página recién publicada y falla si no llega renderizada en servidor. Comprobar el código de estado no serviría de nada: una aplicación con el SSR roto responde igualmente 200 con un esqueleto vacío, que es exactamente como este fallo pasó inadvertido durante horas. La comprobación honesta es buscar la marca que Angular deja en el HTML cuando lo ha renderizado el servidor.

if grep -q 'ng-server-context="ssr"' <<<"$body"; then
  echo "Server-rendered: $(wc -c <<<"$body") bytes"
else
  echo "::error::No ng-server-context — la app cayó a renderizado en cliente."
  exit 1
fi

El parámetro aleatorio que acompaña a la petición evita leer una respuesta cacheada de un despliegue anterior, que daría por bueno lo que ya no se está comprobando.

7. Limitaciones conocidas

  • Quitar un libro de la lista de lectura no lo retira de las estanterías donde estuviera.
  • Open Library puede tardar demasiado durante el renderizado en servidor; la página se sirve igualmente, pero en estado de carga.
  • El tamaño de cada elemento de authors no se valida en las reglas, solo el de la lista (sección 4).
  • Las direcciones de cada despliegue quedan tras el acceso de Vercel; producción es pública, condición necesaria para que el renderizado en servidor sirva de algo.

8. Conclusiones

Separar con precisión qué ocurre en el servidor y qué en el navegador resultó ser la decisión estructural del proyecto: de ahí salen el modo de renderizado de cada ruta, la carga dinámica de Firestore y la espera del guard antes de decidir. Las tres son la misma idea aplicada en tres sitios distintos.

Las reglas de seguridad demostraron que el diseño del modelo de datos es el diseño de la seguridad: colocar el identificador del dueño en la ruta del documento convierte la comprobación de propiedad en algo que no depende de ningún campo escribible por el cliente.

Del pipeline, la lección fue que unas pruebas que no bloquean nada son un informe, no una garantía. Desactivar el despliegue automático para encadenarlo detrás de las pruebas end-to-end, y verificar después que lo publicado viene efectivamente renderizado, es lo que convierte el conjunto en algo en lo que apoyarse.

9. Método de trabajo

El proyecto se construyó con asistencia de herramientas de IA, y el repositorio lo declara: CLAUDE.md, versionado junto al código, recoge las convenciones e instrucciones con las que se trabajó.

Las decisiones que este informe documenta no salieron de esa asistencia, sino de observar el sistema en funcionamiento: desactivar el despliegue automático vino de comprobar que una suite en rojo alcanzaba producción igualmente, y la verificación de ng-server-context, de un fallo que pasó horas inadvertido porque una aplicación con el renderizado roto responde 200 con un esqueleto vacío. Son correcciones sobre algo que ya funcionaba y que, mirado por encima, parecía correcto. Esa es la parte que no se delega.
